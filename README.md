# Knowledge base pipeline

Собирает и чинит базу знаний ассистента поддержки с помощью GigaChat. Два
сценария:

1. **Из выгрузки обращений пополнить базу** (`make run CONFIG=...`). Вход —
   Excel с парами «вопрос — решение». Выход — Excel базы для ревью.
2. **Из плохой базы сделать хорошую** (`make repair-base CONFIG=...`). Вход —
   Excel с колонками «Вопрос» и «Ответ». Выход — Excel исправленной базы и
   Excel того, что в неё не вошло, с причиной.

## Конфиги

Каждая команда получает один аргумент — путь к TOML-конфигу:
`make run CONFIG=configs/supplier-portal-sap.toml`. В конфиге только то, что
нужно этой команде, и только Excel-файлы: что читать и в какую папку писать.

- `name` — название базы. По нему хранятся технические данные базы, и с него
  начинается имя выходного файла: `<name>_<дата>.xlsx`, например
  `Портал поставщика SAP_2026-10-02.xlsx`. Каждый прогон пишет файл со своей
  датой, прошлые версии остаются рядом.
- `output_dir` — папка для выходных Excel-файлов.
- `[domain]` — что говорится модели: `name` подставляется во все промпты
  («служба поддержки <name>»), `[domain.categories]` — категории: ключ
  хранится в записи, описание видит модель.

Неизвестный ключ в конфиге — ошибка, так что опечатка не пройдёт молча.

Конфиг пополнения базы (`configs/supplier-portal-sap.toml`) ещё содержит
`merge_strategy` и таблицу `[dump]`: путь к одному дампу и его колонки
(`question_columns`, `answer_columns`, `extra_columns`). Название базы от имени
дампа не зависит: новый дамп — новый путь в `[dump].path`, база та же.

Конфиг чистки базы (`configs/supplier-portal-sap-dedupe.toml`) — только общие
поля: какую базу чистить и куда выгрузить результат.

Конфиг починки — общие поля и таблица `[input]` с путём к базе для починки и
её колонками:

```toml
name = "Портал поставщика SAP починка"
output_dir = "output"

[input]
path = "~/Desktop/База знаний.xlsx"
question_columns = ["Вопрос"]
answer_columns = ["Ответ"]

[domain]
name = "портала поставщика SAP"

[domain.categories]
how_to = "как выполнить действие: где найти, как создать, изменить, настроить"
# ...
```

Технические настройки — модель, потоки, повторы, пороги, лимиты, оформление
Excel и каталог технических данных — в `config.py`.

## Технические данные

Всё, что прогоны хранят для себя, лежит в `data/` (`config.DATA_DIR`) и
отделено от выходных файлов:

- `data/bases/<name>/` — база пополнения и чистки: `knowledge_base.json`
  (источник правды, Excel — только его витрина), `processed_dumps.json`
  (реестр обработанных дампов), `staging/` (промежуточные файлы прогонов),
  `backups/` (копии базы перед каждой записью);
- `data/repairs/<name>/` — промежуточные файлы починки;
- `data/embeddings.npz` — кэш эмбеддингов вопросов, общий для всех баз;
- `logs/` в каталоге базы — предупреждения и ошибки, отдельный файл на каждый
  прогон (`data/logs/` — для `inspect` и `models`).

## Подготовка

1. `cp .env.example .env` и заполнить: `PYTHON` — интерпретатор для venv,
   `SBEROSC_TOKEN` — токен зеркала PyPI (без него пакеты ставятся из
   публичного PyPI).
2. Сертификаты GigaChat положить в `.gigachat/` (`client-cert.pem`,
   `client-cert.key`; в git не попадают).
3. Завести конфиг базы в `configs/` (см. «Конфиги»).

## Запуск

```bash
make setup          # venv, uv, зависимости из requirements.txt
make inspect CONFIG=configs/supplier-portal-sap.toml      # сверить колонки входного файла и проверить, что GigaChat и эмбеддинги отвечают
make models                                              # список моделей, доступных по нашему сертификату
make run CONFIG=configs/supplier-portal-sap.toml          # сценарий 1: пополнить базу из дампа
make dedupe-base CONFIG=configs/supplier-portal-sap-dedupe.toml  # сценарий 1: чистка накопленной базы
make repair-base CONFIG=configs/<имя>-repair.toml        # сценарий 2: починить плохую базу
make help           # все команды
```

`source activate.sh` активирует тот же venv с теми же переменными, что и
Makefile, — для ручного запуска скриптов.

`make run`, `make dedupe-base` и `make repair-base` идут под `caffeinate`, который не даёт маку
уснуть: прогон на несколько тысяч обращений занимает часы, а во сне сетевые
вызовы обрываются. Экран при этом гаснуть будет.

Прогон можно прервать (Ctrl+C) и запустить снова — он продолжит с места
остановки.

## Устройство кода

`config.py` в корне — технические настройки, `configs/` — TOML-конфиги
прогонов. Код — в `kb/`:

- `kb/utils/` — общие утилиты без логики базы знаний: чтение конфигов, вызовы
  GigaChat, хранение, Excel, логи, обработка строк с возобновлением;
- `kb/steps/` — шаги, каждый делает одно: отбор, переписывание, починка,
  поиск кандидатов, дедупликация, вливание в базу;
- `kb/scenarios/` — сценарии, собранные из шагов;
- `kb/tools/` — `inspect` и `models`.

## Сценарий 1: из выгрузки обращений пополнить базу

Дамп берётся из `[dump].path` конфига и вливается в базу `name`. Дамп, уже
влитый в эту базу, пропускается по хешу файла в `processed_dumps.json`.
Дампы подаются по очереди, от старого к свежему: более поздний обновляет
совпавшие записи более раннего. Три шага, затем пересобирается Excel.

**1. Отбор и переписывание** — два вызова модели на обращение. Фильтр проверяет четыре
признака: переиспользуем ли вопрос, содержит ли ответ инструкцию (а не разовое
действие оператора), полон ли он, нет ли приватных данных. Признаки
ставит модель, решает код: не прошла пара один признак (`MAX_DOUBTFUL_FLAGS`
в `config.py`) — она **спорная**: остаётся в базе, а в Excel её строка жёлтая,
причина — в колонке «Почему спорная» («ответ может быть неполным»). Не прошла
два и больше — уходит в `rejected.json` с причиной. Спорная запись, слитая с
подтверждённой из другого обращения, спорной быть перестаёт. Прошедшие
переписываются в канонический вид с категорией из `[domain.categories]`
конфига.

**2. Дедупликация выгрузки** — схлопывание дублей внутри выгрузки. Кандидаты ищутся
локально, без модели, по трём сигналам сразу: близость эмбеддингов вопросов
GigaChat (единственный сигнал, который видит перефразировку), триграммы
вопроса и триграммы ответа. Затем модель по каждой паре решает, один ли это
вопрос и как соотносятся ответы:

| Связь ответов | Что происходит |
|---|---|
| `same` | слияние в одну полную запись |
| `alternatives` | запись становится списком возможных причин |
| `contradiction` | не сливаются, обе остаются, warning в лог |

Группы строятся вокруг представителя: запись входит в группу, только если
модель подтвердила её именно с представителем. Цепочка A~B, B~C группу не
создаёт — дубликатность нетранзитивна. Группа сливается в два шага, чтобы в
списке причин не было повторов: сначала одинаковые ответы — в один, потом
разные причины — в список.

**3. Вливание в базу** — вливание в актуальную базу. Кандидаты ищутся теми же тремя
сигналами, что и дедупликация. Поведение при совпадении задаёт
`merge_strategy` конфига: `accumulate` дописывает новую причину к старой,
`replace` вытесняет старый ответ. Одинаковые и противоречащие ответы
заменяются свежими при любой стратегии.

**4. Выгрузка в Excel** — Excel из базы с закреплённой шапкой и автофильтром.

Пока нет доступа к модели эмбеддингов, в `config.py` ставится
`EMBEDDING_BACKEND = "none"`: кандидаты ищутся только по триграммам. Кэш
эмбеддингов — `data/embeddings.npz`, привязан к тексту вопроса и
общий для всех шагов: база эмбеддится один раз, дальше платят только новые
вопросы.

### Дедупликация накопленной базы

Пайплайн сравнивает новую выгрузку с базой, но записи базы между собой не
сравнивает вовсе, а сопоставление один-к-одному оставляет второй дубль в базе
нетронутым. `make dedupe-base` запускается вручную, время
от времени: кандидатов ищет по эмбеддингам и триграммам вопросов, категорию
не учитывает, дальше та же модельная проверка пар и двухшаговое слияние, что
внутри выгрузки. Без эмбеддингов порог триграмм намного ниже
(`TRIGRAM_ONLY_CANDIDATE_THRESHOLD`) — вызовов модели будет много, но это
разовая чистка.

Кэш вердиктов — `data/bases/<name>/staging/base_dedupe/verdicts.json`, привязан к
содержимому записей, так что повторный запуск после изменения базы безопасен.

## Сценарий 2: из плохой базы сделать хорошую

Путь к базе и её колонки — в таблице `[input]` конфига починки. Колонки
«Вопрос» и «Ответ» читают и Excel этого проекта.

Разные конфиги можно запускать параллельно, в двух терминалах: у каждого свои
технические данные. Один и тот же конфиг в двух терминалах запускать нельзя. Лимит запросов GigaChat у терминалов общий: на
ответ 429 «Too many requests» все потоки процесса вместе делают паузу, и она
растёт, пока 429 не прекратятся — попытки при этом не тратятся. Если 429
идут постоянно, уменьшите `WORKER_COUNT` в `config.py`.

Здесь нет проверки «нужна ли запись в базе» и «разовый ли это ответ» —
запись уже в базе. Проверяется только полнота, одним вызовом модели на
строку:

- размытый вопрос, просьба или тема («Хочу ноутбук», «Складские запасы»,
  пустой) переписывается по ответу; если ответ отвечает не совсем на вопрос,
  вопрос переписывается под ответ — знание в ответе, вопрос лишь его ищет;
- неполный ответ («Только через техподдержку») дополняется из вопроса;
- оба приводятся к понятному формату: без приветствий и подписей; ФИО
  ответственных и их контакты, ссылки и коды сохраняются;
- ответ ссылкой на инструкцию или шаблон, отсылка к роли, регламентный ответ
  без прямого «да/нет» считаются полными;
- не входит в базу только строка, в ответе которой нет сути: пустой или
  оборванный ответ, реплика из переписки, ответ, который ничего не объясняет.
  Строка без ответа не входит сразу, без вызова модели.

Ответ может быть до 500 слов (`REPAIR_MAX_ANSWER_WORDS`) — в базе бывают
длинные регламентные ответы.

Затем дедупликация по всей базе — так же, как в сценарии 1. Результат в
`output_dir`: `<name>_<дата>.xlsx` — исправленная база,
`<name>_<дата>_rejected.xlsx` — что не вошло: строка источника, причина, вопрос и ответ, а
если запись отклонила проверка кода — ещё и вопрос с ответом, которые написала
модель.
Базы сценария 1 не меняются.

## Стиль текстов

Все промпты, которые пишут вопрос или ответ базы, требуют одного стиля — «Пиши,
сокращай» Ильяхова: коротко, без канцелярита и воды, глагол вместо
отглагольного существительного, сразу к сути, без потери фактов и ссылок.
Правила лежат в одном месте — `kb/utils/prompts.py`, `WRITING_STYLE`.

Ссылки модель не переписывает: GigaChat портит длинные закодированные ссылки.
Перед вызовом код заменяет каждую ссылку меткой «[ссылка-1]», модель
переносит метку в ответ, а код возвращает исходную ссылку дословно. Если модель
придумала метку, которой в записи нет, её спрашивают ещё раз и подсказывают,
какие метки есть, — всего до трёх раз (`LINK_PLACEHOLDER_ATTEMPTS`).

## Защита от ошибок модели

Каждая сгенерированная запись проверяется кодом: категория из списка, лимиты
длины, каждая ссылка ответа дословно есть в исходном тексте (модель не
«исправила» её и не взяла из примера в промпте), и главное — все числа
итогового ответа встречаются в исходном тексте. Число словами в источнике
(«десять») засчитывается как цифры. Слияние проверяется ещё и на длину: список причин обязан быть не
короче самого длинного исходного ответа.

Если проверка не пройдена, ничего не теряется. Группа с разными причинами
остаётся отдельными записями, группа с одинаковыми ответами оставляет самую
подробную запись с источниками всех.

## Возобновление

Оба сценария пропускают строки, которые уже обработаны; строки, на которых
модель так и не дала ответа (`*_failed`), при возобновлении обрабатываются
заново — сбой не отказ. Дедупликация берёт готовые вердикты из
`verdicts.json`, вливание в базу — из `match_verdicts.json`. Все файлы лежат в
`staging/<файл>-<хеш>/` технического каталога базы;
вердикты привязаны к содержимому записей, а не к их номерам. База пишется
атомарно — битого JSON при падении не будет.

Чтобы прогнать всё заново: `FORCE_REPROCESS = True` в `config.py`. Это игнорирует
и реестр, и промежуточные файлы, и кеш вердиктов — нужно после правки
промптов.

## Настройка под другой домен

Новый домен — новый конфиг в `configs/`: `[domain]` и колонки дампа; в
колонках можно перечислить несколько.

Пороги дедупликации — в `config.py`. Нижние (`CANDIDATE_THRESHOLD`, `MATCH_THRESHOLD`)
отбирают пары по похожести вопросов, отдельные пороги по ответам ловят случай,
когда поддержка вставила одну и ту же инструкцию в ответ на разные симптомы.

## Что смотреть после прогона

Сводку причин отказа в логе: если одна причина съедает большую часть, дело в
формулировке признака, а не в данных. Отбракованные пары с исходным текстом —
в `rejected.json` в staging-каталоге дампа. Предыдущая версия базы перед
каждым слиянием копируется в `data/bases/<name>/backups/`.

## Логи

В терминале — ход работы: прогресс-бар каждого шага (сделано/всего, сколько
прошло и сколько осталось), а над ним — только то, что пошло не так: строка,
отклонённая или упавшая, с каждым вызовом модели (шаг, секунды, итог;
медленные — жёлтым от `SLOW_CALL_SECONDS`, красным от вдвое большего), пара
без вердикта или с противоречащими ответами. В конце прогона — таблица вызовов
модели по шагам (сколько, сколько упало, среднее, максимум, всего) и путь к
лог-файлу.

Предупреждения и ошибки — в лог-файл прогона
`data/bases/<name>/logs/<команда>_<время>.log` (у починки —
`data/repairs/<name>/logs/`). Файл создаётся, только если есть что записать.
Там видно, почему строка стала `filter_failed`: ошибка GigaChat, непрошедшая
проверка схемы или ответ модели текстом без вызова функции — с самим ответом
модели. Падение прогона тоже пишется туда, с трассировкой.
