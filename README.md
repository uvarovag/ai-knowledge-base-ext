# Knowledge base pipeline

Собирает и чинит базу знаний ассистента поддержки с помощью GigaChat. Два
сценария:

1. **Из выгрузки обращений пополнить базу** (`make run`). Вход — Excel с
   парами «вопрос — решение». Выход — `data/knowledge_base.json` (источник
   правды) и `data/knowledge_base.xlsx` (витрина для ревью).
2. **Из плохой базы сделать хорошую** (`make repair-base`). Вход — Excel с
   колонками «Вопрос» и «Ответ». Выход — `data/repaired/`: исправленная база и
   таблица того, что в неё не вошло, с причиной.

## Подготовка

1. `cp .env.example .env` и заполнить: `PYTHON` — интерпретатор для venv,
   `SBEROSC_TOKEN` — токен зеркала PyPI (без него пакеты ставятся из
   публичного PyPI).
2. Сертификаты GigaChat положить в `.gigachat/` (`client-cert.pem`,
   `client-cert.key`; в git не попадают).
3. Пути к выгрузкам — в `config.DUMP_PATHS`, к базе для починки —
   `config.REPAIR_INPUT_PATH`.

## Запуск

```bash
make setup          # venv, uv, зависимости из requirements.txt
make inspect        # сверить колонки входных файлов и проверить, что GigaChat и эмбеддинги отвечают
make run            # сценарий 1: пополнить базу из новых выгрузок
make dedupe-base    # сценарий 1: дедупликация накопленной базы
make repair-base    # сценарий 2: починить плохую базу
make help           # все команды
```

`source activate.sh` активирует тот же venv с теми же переменными, что и
Makefile, — для ручного запуска скриптов.

`make run`, `make dedupe-base` и `make repair-base` идут под `caffeinate`, который не даёт маку
уснуть: прогон на несколько тысяч обращений занимает часы, а во сне сетевые
вызовы обрываются. Экран при этом гаснуть будет.

Прогон можно прервать (Ctrl+C) и запустить снова — он продолжит с места
остановки.

## Устройство кода

`config.py` в корне — все настройки. Код — в `kb/`:

- `kb/utils/` — общие утилиты без логики базы знаний: вызовы GigaChat,
  хранение, Excel, логи, обработка строк с возобновлением;
- `kb/steps/` — шаги, каждый делает одно: отбор, переписывание, починка,
  поиск кандидатов, дедупликация, вливание в базу;
- `kb/scenarios/` — сценарии, собранные из шагов;
- `kb/tools/` — `inspect`.

## Сценарий 1: из выгрузки обращений пополнить базу

Выгрузки берутся из `config.DUMP_PATHS` в указанном порядке. Уже обработанные
пропускаются по хешу файла в `processed_dumps.json`. Для каждой — три шага,
затем один раз пересобирается Excel.

**1. Отбор и переписывание** — два вызова модели на обращение. Фильтр проверяет четыре
признака: переиспользуем ли вопрос, содержит ли ответ инструкцию (а не разовое
действие оператора), полон ли он, нет ли приватных данных. Отказ хотя бы по
одному — пара уходит в `rejected.json` с причиной. Прошедшие переписываются в
канонический вид с категорией из `config.CATEGORIES`.

**2. Дедупликация выгрузки** — схлопывание дублей внутри выгрузки. Кандидаты ищутся
локально, без модели, по трём сигналам сразу: близость эмбеддингов вопросов
GigaChat (единственный сигнал, который видит перефразировку), триграммы
вопроса и триграммы ответа. Затем модель по каждой паре решает, один ли это
вопрос и как соотносятся ответы:

| Связь ответов | Что происходит |
|---|---|
| `same` | слияние в одну полную запись |
| `alternatives` | запись становится списком возможных причин |
| `contradiction` | не сливаются, обе остаются, warning в лог |

Группы строятся вокруг представителя: запись входит в группу, только если
модель подтвердила её именно с представителем. Цепочка A~B, B~C группу не
создаёт — дубликатность нетранзитивна. Группа сливается в два шага, чтобы в
списке причин не было повторов: сначала одинаковые ответы — в один, потом
разные причины — в список.

**3. Вливание в базу** — вливание в актуальную базу. Кандидаты ищутся теми же тремя
сигналами, что и дедупликация. Поведение при совпадении задаёт
`config.MERGE_STRATEGY`: `accumulate` дописывает новую причину к старой,
`replace` вытесняет старый ответ. Одинаковые и противоречащие ответы
заменяются свежими при любой стратегии.

**4. Выгрузка в Excel** — Excel из базы с закреплённой шапкой и автофильтром.

Пока нет доступа к модели эмбеддингов, в `config.py` ставится
`EMBEDDING_BACKEND = "none"`: кандидаты ищутся только по триграммам. Кэш
эмбеддингов — `data/staging/embeddings.npz`, привязан к тексту вопроса и
общий для всех шагов: база эмбеддится один раз, дальше платят только новые
вопросы.

### Дедупликация накопленной базы

Пайплайн сравнивает новую выгрузку с базой, но записи базы между собой не
сравнивает вовсе, а сопоставление один-к-одному оставляет второй дубль в базе
нетронутым. `make dedupe-base` запускается вручную, время
от времени: кандидатов ищет по эмбеддингам и триграммам вопросов, категорию
не учитывает, дальше та же модельная проверка пар и двухшаговое слияние, что
внутри выгрузки. Без эмбеддингов порог триграмм намного ниже
(`TRIGRAM_ONLY_CANDIDATE_THRESHOLD`) — вызовов модели будет много, но это
разовая чистка.

Кэш вердиктов — `data/staging/base_dedupe/verdicts.json`, привязан к
содержимому записей, так что повторный запуск после изменения базы безопасен.

## Сценарий 2: из плохой базы сделать хорошую

`make repair-base` читает `config.REPAIR_INPUT_PATH` — по умолчанию
`data/base_to_repair.xlsx` с колонками «Вопрос» и «Ответ», так что можно
подать и `knowledge_base.xlsx` этого проекта. Колонки меняются в
`REPAIR_QUESTION_COLUMNS` и `REPAIR_ANSWER_COLUMNS`.

Здесь нет проверки «нужна ли запись в базе» и «разовый ли это ответ» —
запись уже в базе. Проверяется только полнота, одним вызовом модели на
строку:

- неполный вопрос («Складские запасы», пустой) восстанавливается по ответу;
- неполный ответ («Только через техподдержку») дополняется из вопроса;
- оба приводятся к понятному формату: без приветствий, ФИО заменены ролью,
  ссылки и коды сохранены;
- если ни то ни другое сделать нельзя — строка не входит в базу; строка без
  ответа не входит сразу, без вызова модели.

Затем дедупликация по всей базе — так же, как в сценарии 1. Результат в
`data/repaired/`: `knowledge_base.json` и `.xlsx` — исправленная база,
`rejected.xlsx` — что не вошло: строка источника, причина, вопрос и ответ.
Живая база сценария 1 не меняется.

## Защита от ошибок модели

Каждая сгенерированная запись проверяется кодом: категория из списка, лимиты
длины, и главное — все числа итогового ответа должны встречаться в исходном
тексте. Слияние проверяется ещё и на длину: список причин обязан быть не
короче самого длинного исходного ответа.

Если проверка не пройдена, ничего не теряется. Группа с разными причинами
остаётся отдельными записями, группа с одинаковыми ответами оставляет самую
подробную запись с источниками всех.

## Возобновление

Оба сценария пропускают строки, которые уже обработаны; строки, на которых
модель так и не дала ответа (`*_failed`), при возобновлении обрабатываются
заново — сбой не отказ. Дедупликация берёт готовые вердикты из
`verdicts.json`, вливание в базу — из `match_verdicts.json`. Все файлы лежат в
`data/staging/<файл>-<хеш>/` (для сценария 2 — `repair-<файл>-<хеш>/`);
вердикты привязаны к содержимому записей, а не к их номерам. База пишется
атомарно — битого JSON при падении не будет.

Чтобы прогнать всё заново: `FORCE_REPROCESS = True` в конфиге. Это игнорирует
и реестр, и промежуточные файлы, и кеш вердиктов — нужно после правки
промптов.

## Настройка под другой домен

В `config.py`: `DOMAIN_NAME` подставляется во все промпты, `CATEGORIES` задаёт
список категорий (ключ хранится в записи, значение показывается модели),
`QUESTION_COLUMNS` / `ANSWER_COLUMNS` — колонки выгрузки, можно перечислить
несколько.

Пороги дедупликации там же. Нижние (`CANDIDATE_THRESHOLD`, `MATCH_THRESHOLD`)
отбирают пары по похожести вопросов, отдельные пороги по ответам ловят случай,
когда поддержка вставила одну и ту же инструкцию в ответ на разные симптомы.

## Что смотреть после прогона

Сводку причин отказа в логе: если одна причина съедает большую часть, дело в
формулировке признака, а не в данных. Отбракованные пары с исходным текстом —
в `rejected.json` в staging-каталоге выгрузки. Предыдущая версия базы перед
каждым слиянием копируется в `data/backups/`.

Все предупреждения и ошибки дописываются в `data/errors.log`. Там видно, почему
строка стала `filter_failed`: ошибка GigaChat, непрошедшая проверка схемы или
ответ модели текстом без вызова функции — с самим ответом модели.
